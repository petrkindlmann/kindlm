<decisions>
## Implementation Decisions

All findings below were reproduced at runtime (built `@kindlm/core` + fake provider + real
runner/parser). Each is a LOCKED decision.

### #1 — Strict config schema (Critical)
- **Root cause:** `packages/core/src/config/schema.ts` — `.strict()` count is 0. Unknown keys
  under `expect` (and everywhere) are silently stripped, so a typo'd `tooCalls`/`guardrailz`
  validates clean and the test runs with **0 assertions**, status `passed`.
- **Decision:** Apply `.strict()` to assertion-bearing sub-schemas at minimum: `ExpectSchema`,
  `ToolCallExpectSchema`, `GuardrailsSchema`, `OutputExpectSchema`, `PIIGuardrailSchema`,
  `KeywordGuardrailSchema`, `JudgeCriterionSchema`, `BaselineDriftSchema`. Prefer repo-wide
  `.strict()` on every config sub-schema, but verify nothing legitimately passes extra keys
  (e.g. `argsSchemaResolved` is parser-populated on `ToolCallExpectSchema` — must remain allowed).
- **UX:** In `validate` command, catch Zod `unrecognized_keys` and print a "did you mean?"
  suggestion (Levenshtein ≤2 against known sibling keys). v2.2.0 already shipped "did you mean"
  for prompt/model refs — reuse that helper pattern (`config/zod-path.ts` exists).

### #2 — Inject argsSchema validator into assertion context (High)
- **Root cause:** `packages/core/src/engine/runner.ts` `buildAssertionContext` (~line 388) and the
  per-turn + command contexts NEVER set `context.validateJsonSchema`. So
  `assertions/tool-calls.ts:76` always hits the "argsSchema provided but no JSON Schema validator
  was injected" guard. Schema *content* already resolves into `argsSchemaResolved` (parser) and
  reaches the assertion via `registry.ts` — only the validator function is missing.
- **Decision:** Build an AJV-backed `validateJsonSchema` and inject it into every AssertionContext
  the runner constructs (final, per-turn, command). Reuse the exact AJV setup from
  `assertions/schema.ts` (`new Ajv({ allErrors: true, strict: false })` + `ajv-formats`,
  compiled-validator cache). Do not duplicate AJV config — extract a shared helper if needed.
  Core stays I/O-free (AJV is a pure dep, already used).

### #3 — Opt-in tool-call ordering (High) — BROAD scope
- **Root cause:** `assertions/registry.ts:28` builds `createToolOrderAssertion` only when some
  `tc.order !== undefined`. A plain `toolCalls` list is presence-only, so refund-before-lookup
  passes a test listing them in safe order.
- **Decision (broad):** Restructure the `toolCalls` expectation to support an explicit ordered
  form without breaking the existing two shapes (plain list = presence-only; numeric `order:` =
  positional). Add an `ordered: true` opt-in (object form `{ ordered: true, calls: [...] }` OR a
  sibling `toolCallOrder: [name, ...]` — planner picks the cleaner schema, must preserve
  back-compat with the current array form). When ordered, build `createToolOrderAssertion` from
  the declared sequence. Update Zod schema, `registry.ts`, VS Code schema/completions, and the
  YAML template/docs. The existing `createToolOrderAssertion` in `assertions/tool-calls.ts` is
  reused as-is.

### #4 — Real version in JSON reporter (High for a compliance product)
- **Root cause:** `packages/cli/src/utils/select-reporter.ts` calls `createJsonReporter()` with
  no argument → `reporters/json.ts:11` stamps `version ?? "0.0.0"`. For an installed binary,
  `process.env.npm_package_version` is undefined. Compliance metadata is already correct
  (`commands/test.ts:269` passes the bundler-injected `KINDLM_VERSION`).
- **Decision:** Pass the bundler-injected `KINDLM_VERSION` constant into `createJsonReporter` from
  `select-reporter.ts` (it already `declare const KINDLM_VERSION` in test.ts — make it available
  to select-reporter, e.g. via a shared declaration or by threading it through). Single source of
  truth so `--version`, JSON report, and compliance never diverge.

### #5 — PII detector framework (Medium) — BROAD scope
- **Root cause:** `assertions/pii.ts` has ZERO built-in detectors; it only compiles user
  `denyPatterns` (3 Zod-schema defaults: dashed-SSN, CC, email) + `customPatterns`. Undashed SSN,
  US/intl phone, IBAN, IP, JWT, AWS key all MISSED.
- **Decision (broad):** Build a named-detector registry in core. Each detector = `{ name, pattern,
  optional validator }`. Ship: `ssn` (dashed+undashed), `credit_card` (Luhn-checked),
  `email`, `phone` (US + E.164), `iban` (mod-97 checksum), `ip` (v4), `jwt`, `api_key`
  (`AKIA`/`sk-`/`ghp_`/`xox` prefixes). Add a `detectors: [...]` config list under
  `guardrails.pii` (default = current 3 for back-compat). Locale packs (e.g. Czech rodné číslo)
  enabled by name without a core change. Keep the existing ReDoS nested-quantifier guard. Update
  README to list only detectors that actually fire (honesty), plus the new configurable set.

### #6 — --no-cache regression test (Medium) — ALREADY FIXED
- **Status:** `cli/utils/init-adapters.ts:130` skips wrapping the caching adapter entirely when
  `noCache`, so there is no read path. The npm-2.3.0 symptom is gone in local source.
- **Decision:** No code change. Add a regression test: two consecutive `--no-cache` runs against a
  counter-incrementing provider must return distinct responses (proving reads are not served).
</decisions>
