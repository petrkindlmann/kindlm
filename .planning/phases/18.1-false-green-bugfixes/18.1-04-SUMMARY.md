# Phase 18.1 Plan 04: Opt-in Tool-Call Ordering Summary

Adds an opt-in `toolCallsOrdered: true` sibling flag so a plain `toolCalls` list can enforce the DECLARED call sequence (out-of-order FAILS), reusing the existing `createToolOrderAssertion` by synthesizing order indices from array position — while preserving both back-compat behaviors.

## Zod shape chosen

Sibling boolean on `ExpectSchema`: `toolCallsOrdered: z.boolean().optional()`. Declared explicitly so plan 01's `.strict()` ExpectSchema accepts it; a typo'd `toolCallOrdered` is rejected by strict mode.

## Registry wiring

`createAssertionsFromExpect` computes `useOrdered = hasNumericOrder || toolCallsOrdered === true`. When ordered solely via the opt-in, it synthesizes `order: <position>` from the entry's index among positive calls (skipping `shouldNotCall` negatives) and passes the mapped entries to the existing `createToolOrderAssertion`. The numeric-order and plain-list presence-only paths are untouched.

## Three back-compat behaviors (all test-verified)

| Mode | Config | Behavior | Test |
|------|--------|----------|------|
| Plain (presence-only) | `toolCalls` only | Passes regardless of call order; 2 separate `tool_called` assertions | registry.test.ts "back-compat: plain list … presence-only" (runs refund-then-lookup, all pass) |
| Numeric positional | entries with `order:` | Unchanged positional matching → single `tool_order` | registry.test.ts "back-compat: numeric order: …" |
| Ordered opt-in | `toolCallsOrdered: true` | In-order PASSES, out-of-order FAILS with `TOOL_CALL_ORDER_WRONG` | registry.test.ts ordered PASS + ordered FAIL cases |

The FAIL case asserts an "at position" result with `failureCode === "TOOL_CALL_ORDER_WRONG"`.
